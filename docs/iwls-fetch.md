# IWLS fetching contract

Version 2. Implementations conform to [`fixtures/iwls-fetch.json`](../fixtures/iwls-fetch.json), which contains synthetic stations and samples. `SlackwaterIWLS` is the Swift reference client, and [`slackwater-iwls`](../kotlin/README.md#iwls-fetching) is the Kotlin client for Android. [`benchmarks/iwls.ts`](../benchmarks/iwls.ts) is an unpublished TypeScript implementation for this repository's scripts, for the CHS fit benchmark’s fetching path. Its benchmark-specific cache adapters have separate persistence policy; their migration is tracked in [#439](https://github.com/openwatersio/slackwater/issues/439) and [#440](https://github.com/openwatersio/slackwater/issues/440). This contract covers fetching inputs for local CHS fitting; the prediction engines remain independent of runtime I/O.

## Resolve a station

Fetch `https://api-iwls.dfo-mpo.gc.ca/api/v1/stations`. Retain stations whose `timeSeries` includes the requested series (`wlp` for tides, `wcsp1` for current speed). Choose the nearest by spherical haversine distance with radius 6371.0088 km, retaining list order on ties. Accept a distance of at most 3 km; fail permanently when there is no candidate or the nearest is farther away. Names and station codes are display metadata. Every subsequent request uses the resolved `id`, encoded as one URL path component: `/`, `%`, `?`, and `#` escaped and the other sub-delimiters kept, as the fixture's `pathComponents` rows show. Refuse an empty `id`, and an `id` of `.` or `..`, as an invalid request; URL resolution removes those dot segments whether or not they are escaped.

The application supplies valid geographic coordinates. Resolving a current station by `wcsp1` does not guarantee `wcdp1` or flood/ebb metadata exists; the consumer validates those inputs before fitting.

## Plan the window

The caller supplies the current instant and the station's IANA time zone. Find the start of that local calendar day. The device's time zone does not determine the fit end. Use an up-to-date time-zone database; DST days can contain 23 or 25 elapsed hours.

For a nominal positive, finite duration `days`, an end instant `end` in epoch seconds, and `week = 604800`:

1. Set `t = floor((end - days * 86400) / week) * week`.
2. While `t < end`, emit `[t, min(t + week, end)]` and advance `t` by `week`.
3. Return the chunks in reverse order, newest first.

Here `days` denotes an elapsed fit duration. Calendar arithmetic determines the midnight anchor; fixed seconds determine the absolute cache grid. Floor rounds toward negative infinity, including before 1970. A plan spans at least N and less than N + 7 elapsed days. It has no zero-length chunk when the end falls on the grid. The newest portion of a 210-day plan equals the 60-day plan at the same end. Consumers concatenate the complete chunks, including the oldest chunk's extra samples.

Each request spans at most seven elapsed days. A durable chunk has a full 604800-second duration and starts on the absolute epoch-week grid. Its identity includes the resolved ID, series, both endpoints, and sample step. Partial chunks must be fetched again when their end changes.

A nonempty week is eligible for permanent caching only when it contains both exact endpoints and every sample is finite, within the inclusive window, and on the selected grid. Interior gaps, repeated timestamps, and response order do not affect eligibility. A response missing either endpoint is ineligible and must be fetched again. This deliberately refetches genuine endpoint gaps too, rather than retaining a possibly truncated week permanently. A successfully decoded and grid-filtered empty week, including a response whose samples are all skipped, can be cached for 86400 elapsed seconds from receipt; at expiry or when the clock precedes receipt, fetch it again. Empty bodies are transport failures, not empty weeks.

The shared cache-entry carrier records `startMs`, `endMs`, `sampleMinutes`, `fetchedAtMs`, and `samples`. All timestamps use Unix milliseconds. Reuse validates identity and sample eligibility again; metadata cannot promote a truncated week. Positive entries do not expire. Legacy raw arrays may be reused only for a 15-minute request after filtering and endpoint validation; legacy empty arrays have no receipt time and must be fetched again. The Swift client optionally accepts `IwlsChunkCache(directory:)`, which owns disk persistence, atomic replacement, in-process synchronization, backup exclusion, legacy migration, and expiry. Partial windows bypass disk lookup so they cannot remove a complete week with the same start; writes on other grids preserve legacy 15-minute files. Its fetch-through path preserves a complete positive week over a concurrent empty or partial response. Call `purge(stationID)` after fitting to remove positive chunks and expired empty entries, `purge(stationID, includingEmpty: true)` for orphan cleanup, or `reset()` to remove the dedicated directory. `series(cache: false)` bypasses reads and writes; `cacheEmpty: false` bypasses negative hits and writes while retaining positive reuse. Other implementations may supply their own storage adapter using the shared carrier. Applications configure storage and request cleanup; resume UI remains application-owned. The iOS adapter caches the station list for seven elapsed days and falls back to a stale decoded list after a fetch failure.

## Request and decode samples

Use `GET /stations/{resolvedID}/data` with query parameters:

- `time-series-code`: one of the fit series `wlp`, `wcsp1`, or `wcdp1`. Reject any other code: the grid filter below would empty event series such as `wlp-hilo`.
- `from`, `to`: the chunk's UTC ISO 8601 endpoints, with second precision and `Z` suffix.
- `resolution`: supplied by the consumer's fit recipe. Supported `sampleMinutes` values are 1, 3, 5, 15, and 60, mapped respectively to `ONE_MINUTE`, `THREE_MINUTES`, `FIVE_MINUTES`, `FIFTEEN_MINUTES`, and `SIXTY_MINUTES`. Reject unsupported steps before sending a request. The default is 15 minutes for existing callers. Networking modules have no dependency on the recipes or prediction engines.

Both endpoints are inclusive. Decode the response array's `eventDate` and numeric `value` fields, keeping response order. Reject malformed JSON or missing required fields. Accept ISO 8601 date-times with whole seconds and a UTC designator or numeric offset; skip unparseable dates and fractional-second strings, including `.000Z`. Remove a timestamp only when it equals the last successfully appended timestamp in that response; retain its first value. This is adjacent suppression, not a global deduplication or a sort.

Represent a decoded sample as `{t, v}`, where `t` is Unix epoch milliseconds and `v` is the provider value without unit conversion. Tide heights are in meters, current speeds in knots, and directions in degrees. The consumer projects speed and direction before fitting.

Keep only samples with `t % (sampleMinutes * 60000) == 0`, even when the provider was asked for that resolution. Apply the same filter to cache hits. A cache entry can satisfy only a request with the same sample step, even when the stored grid is finer. The raw decoder is available separately for recording validation.

Concatenate responses without deduplicating their shared endpoints. Sort the accumulated tide samples by timestamp before fitting. Equal timestamps from separate chunks retain their weight in the fitter.

For current axes, use `GET /stations/{resolvedID}/metadata` and decode optional `floodDirection` and `ebbDirection`. The fitting consumer decides whether missing axes make the job unusable.

## Pace, retry, and cancel

All client instances in a process share a pacer. Admit request starts one at a time, at least 2.5 seconds after the previous admission on a monotonic clock, including station-list, metadata, and retry attempts, so a wall-clock change cannot stretch the gap and a stalled scheduler cannot release a burst. A waiter cancelled before its turn takes no slot. A serial download queue is application policy; pacing alone does not limit in-flight requests. The default Swift URLSession waits for connectivity on Apple platforms and has a 300-second resource timeout. While it waits, an offline device or one denied cellular data fails each attempt as a timeout after 300 seconds rather than at once, and timeouts are retried, so a request can hold the queue for about 20 minutes before it fails. The resource timeout covers the whole transfer, so a link too slow to finish a response in 300 seconds fails the same way. Callers that supply a session own its configuration. The TypeScript client's default fetch bounds each attempt at 300 seconds the same way, and a timed-out attempt is a transient failure. So does the Kotlin client's default transport; it does not wait for connectivity, so an offline request whose lookup or connection fails at once ends as transient after about 15 seconds of retries, while a silent connection waits out its connect/read idle limit; a trickling response can reach the whole-attempt bound. Kotlin additionally limits connect/read idle time to 15 seconds (including the wait for response headers) and response bodies to 8 MiB. It uses eight daemon request workers with no pending-request queue and two separate daemon cleanup workers with at most eight queued disconnects. Request saturation fails transiently. Independent cleanup capacity releases request workers even when response headers trickle in and keep idle timeouts from firing. It requests identity encoding to preserve framing headers on Android. A response over the 8 MiB cap fails permanently without retries.

Try each request at most four times, including its first attempt. `attempt` in the fixture counts the attempt that just failed, starting at one. On a retry:

- HTTP 429: wait `max(60, Retry-After)` seconds.
- HTTP 500–599 except 501, 505, and 511: wait `max(2^attempt, Retry-After)` seconds.
- Transient transport failures: wait `2^attempt` seconds, giving 2, 4, and 8 seconds.
- Other outcomes: do not retry within the client.

`Retry-After` is interpreted as numeric seconds; absent, nonnumeric, negative, and non-finite values use the default delay. A value over 600 seconds waits 600 seconds, so one header cannot hold the queue for hours. The retry can then land inside the window the server named. Failing at once instead would let a serial queue send every other job into that window. Transient failures are timeout, connection failure, host/DNS lookup failure, lost connection, offline, unavailable resource, invalid server response, and empty response. The Swift mapping is `URLError.timedOut`, `cannotConnectToHost`, `cannotFindHost`, `dnsLookupFailed`, `networkConnectionLost`, `notConnectedToInternet`, `resourceUnavailable`, `badServerResponse`, and `zeroByteResource`, plus native POSIX `ECONNABORTED`, `ECONNRESET`, and `ETIMEDOUT`. Use each platform's errno constants; Darwin and Linux assign different numbers. The Kotlin client counts any `IOException` in a failure's cause chain as transient, because JVM and Android stacks report lost links as plain `IOException`s, unless the chain holds a TLS failure with no sign that the link itself dropped. It treats a transport's own timeout as transient too. It reports IWLS's own answers as permanent (HTTP 400–499 except 429, a body that cannot be decoded, or a response over the transport’s body limit); a failure it does not retry, TLS included, reaches the application's queue as transient.

Only HTTP 200 supplies a successful body, and a 200 with an empty body is an empty response, retried as a transient failure. Do not retry body-decoding errors, except that Kotlin treats malformed JSON in a close-delimited HTTP 200 response as a possible truncated transfer and retries within the same four-attempt bound. Without Content-Length or chunked framing, the transport cannot distinguish a dropped link from the end of a response. Well-formed JSON with an invalid schema remains permanent, as does malformed JSON with Content-Length or chunked framing. A custom transport must set `IwlsResponse.closeDelimited` when it detects uncertain framing; the default is false for compatibility. `HttpURLConnection` infers this flag from its exposed headers, so an HTTP/2 implementation that hides its framing can also cause bounded retries of malformed JSON. Cancellation, TLS failures, and policy denials such as disallowed cellular data propagate immediately when the session reports them; the default session's wait above reports them as timeouts. Pacing and backoff waits are cancellable. After the last attempt, HTTP 400–499 except 429 is permanent; other HTTP failures, including an exhausted rate limit, remain transient for the application's queue. The queue owns any later retry schedule.

## Scope and licensing

`SlackwaterIWLS`, the Kotlin `slackwater-iwls` client, this spec, and the synthetic fixtures are MIT-licensed. The Swift client is extracted from the copyright holder's iOS implementation and relicensed with their authorization. The GPL iOS application keeps its own license; the MIT module has no dependency on it or on `SlackwaterKit`.

The client fetches directly for the user's own device. The TypeScript implementation also fetches for this repository's validation benchmark, which keeps responses in its run cache and publishes only scores. It does not authorize redistribution of CHS predictions. Keep it out of `@slackwater/api` and the CLI's prediction-serving paths. The contract fixtures contain no fetched CHS observations or predictions. The prediction engines in TypeScript, Swift, and Kotlin have no dependency on these clients.

## Verification

Run `swift test -c release --filter SlackwaterIWLSTests` and `npx vitest run --project benchmarks` from the repository root, and `./gradlew :slackwater-iwls:test` from `kotlin/`. Each suite consumes the fixture directly and checks the HTTP loop with synthetic responses, without contacting IWLS. Contract changes update the spec, fixture, and every implementing client's tests together. A fixture version change denotes a change to the fetching contract, independently of the harmonic fit recipe.
